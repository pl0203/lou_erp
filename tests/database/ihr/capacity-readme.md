## Logical generation versus materialized snapshot

`buildCapacityFixture()` and `buildCapacitySql()` deterministically reproduce logical input, UUID derivations and SQL text. Source-only generation:

    node tests/database/ihr/capacity-sql.mjs /tmp/ihr-capacity-input.sql

The output must not already exist. This command makes no database connection. The loader requires postgres, pilot_test, PG17, the exact disposable marker, empty iHR state and fresh identity sequences.

**A new materialization is not byte-identical to an earlier materialization.** Product triggers legitimately write actual timestamps. Those clocks flow into full member/assignment snapshots, quote fingerprints and cancellation sources. They must never be stripped, rewritten or overridden merely to reproduce a hash. The logical input/generator/SQL hashes and the actual materialized database fingerprint are separate records.

The supported restoration mechanism is: materialize once, validate it, capture one complete official PostgreSQL logical dump, seal its bytes, and restore that same artifact for the run. Independently rerunning the generator/SQL is not a restore. The coordinator owns dump creation/restoration and terminal process handling after independent control review. The sampler neither implements nor relaxes that lifecycle. Physical backup machinery is not required to preserve the PostgreSQL WAL prelogging counter.

Only each sequence's PostgreSQL WAL/cache prelogging `log_cnt` is excluded from logical equality and its SHA-256. It is returned separately as `diagnostics.sequenceLogCounters`, keyed by the two exact sequence names; optional diagnostics may differ or be absent, but arbitrary diagnostic fields or additional state exclusions are rejected. All relation hashes still cover complete rows, clocks and nested source JSON. Old v2 fingerprints are rejected.

Sequence integer values are lossless decimal strings; booleans remain booleans. This is a distinct representation repair: both pinned migrations declare `sequence bigint GENERATED ALWAYS AS IDENTITY`, whose default maximum `9223372036854775807` exceeds JavaScript's safe integer range. Adjacent values `9223372036854775806` and `9223372036854775807` round to the same JavaScript Number. SQL casts each retained integer to text before JSON serialization, and the verifier rejects numeric/rounded alternatives rather than normalizing them. Every configuration field remains part of exact equality.

SQL independently checks the actual iHR table and sequence inventory against the explicit list; unknown or missing state fails. Fixture identity, marker and scope revision must each have exactly one row. Each relation includes count and SHA-256; a final hash covers the complete retained logical map. ## Coordinator callback API

`runCapacityMeasurement({environment, openSession, restoreBaseline, sealedBaseline, evidence, emit})` is import-only.

- `openSession(connection)` receives the existing validateIhrDbTarget sanitized connection. It returns `{query(sql), close()}`; JSON queries return decoded scalar first columns, and control batches may return an ignored value. The coordinator enforces reviewed query bounds; close resolves only after terminal session closure.
- `sealedBaseline` has format `ihr-capacity-seal-v2`, targetDatabase `pilot_test`, method `coordinator-owned-sealed-logical-dump`, artifact `{sha256,bytes}`, logicalInputHash, sourceCommit, sourceTree, migrationHashes, fixtureGeneratorHash and the v3 logical fingerprint returned by the actual database. Old seals/methods are rejected. Source/evidence pins and logical input must match. The sampler clones/freezes its seal so callbacks cannot silently move the expected state.
- `restoreBaseline({sealedArtifact,expectedFingerprint,expectedHash,sourceCommit,targetDatabase,workload,phase,index})` restores that same artifact only after all relevant sessions are terminally closed. It returns `{artifactSha256,baselineSha256,targetDatabase,restoredFromSealedArtifact:true,terminalSessionsClosed:true}`. The adapter checks that proof and then independently executes identity/cardinality and complete-fingerprint SQL; callback assertions alone never establish restored equality.
- A verified restore trial is mandatory before the first timed workload. The same process runs outside every mutation warm-up/sample and before plans. Final read-only plan inspection must leave the sealed fingerprint intact. No other database namespace, clock override, trigger bypass, immutable-row reset or logical rematerialization is supported.
- `evidence` supplies actual CPU/RAM/storage/OS, exact source commit/tree, all applied migration hashes and generator hash. `emit(kind,record)` durably retains metadata, restore proofs, preassertion observations, failures, samples, statistics, plans and index evidence. A failed observation includes workload, phase/index, actual result or error and elapsed time before an assertion can discard context.

The actual materialized snapshot hash and artifact hash are NOT_RUN until the coordinator creates and independently verifies them. Never populate them using the deterministic logical-input hash.

The coordinator's reviewed restore implementation must also establish these conditions before admitting sampler sessions; the sampler's row fingerprint and callback success booleans do not replace independently obtained schema/access evidence:

- Pin official PostgreSQL/dump/restore tool versions, exact driver/source/migration/fixture hashes, dump SHA-256/size and complete object inventory. Close sessions and exclude concurrent mutations/sequence consumers during sealing. Restore only to the same owned `pilot_test`, bounded and fail-on-error, after verified terminal session closure
- Restore the complete archive, including pre-data, data and post-data definitions, before workloads. A data-only insert into an already-triggered schema is unsuitable. Do not disable installed triggers, change replication mode, rewrite immutable rows or regenerate fixture SQL
- Independently compare original and restored definitions and access controls: tables/columns/types/defaults/identity/constraints, sequence ownership/dependencies/persistence/ACLs, functions/security/owners/search paths/configuration, triggers/enabled states, indexes, RLS flags/policies, grants/revokes/default ACLs, relevant role attributes/memberships and database settings. Use stable qualified identities and definitions, not newly allocated catalog OIDs. Database dumps omit cluster-global roles, so verify those unchanged separately. Preserve ownership and ACLs without omission shortcuts
- Record and run the same fixed `ANALYZE` procedure outside timing after each restoration, using the same hardware/version/planner/durability settings. Official logical dumps omit optimizer statistics. Retain actual EXPLAIN/index evidence after restoration, alongside the genuine initial restore trial and independent logical equality checks for every subsequent mutation restoration
- Include normal first-allocation and durable COMMIT costs in timed mutations. Do not pre-consume sequence values or manipulate `log_cnt` to select a faster WAL path. The excluded diagnostic can affect WAL work; consistent restore/ANALYZE establishes the method, not identical internal engine history
