## Source and packet contract

`scripts/build-demo-rollout.mjs` is a library with no connection, apply, deployment or retry side effects. It uses the existing transaction lexer without changing historical rollout scripts.

Required order:

1. `202610081101_demo_order_promotions.sql`
2. `202610081102_demo_visit_workflow.sql`
3. `202610081103_demo_sales_reporting.sql`
4. `202610081104_demo_sales_assignment_cardinality.sql`

Provide a JSON manifest with `version: 1`, `status: "reviewed"`, upstream `18ec064e43466dc8b567482a628b3ef91f886ce4`, and exactly four ordered `sources` entries. Every entry contains the exact repository-relative path, SHA-256 of the complete migration bytes and full reviewed 40-character commit. Pass its separately reviewed SHA-256 as `manifestSha256`; the digest is over `JSON.stringify(manifest)` without additional whitespace. Final source hashes must come from the coordinator's accepted review, not worker status claims or a live hash substituted to silence a mismatch. No final manifest is bundled until those reviews are accepted. `synthetic` manifests can generate fixture packets only.

The checked-in `demo-rollout-protected-sources.json` pins all pre-demo migrations and the existing HR and password-reset/Auth implementation at the verified baseline. Every packet build verifies those files. The wrapper, snapshot query and protection manifest are themselves part of the reviewed release commit; approve the entire final packet hash, not just the four migration hashes.

Use `buildDemoPreflight({target})` to produce the observation packet. It creates only session-local temporary work tables, then takes a PostgreSQL repeatable-read/read-only transaction for catalog and protected-row fingerprints, rolls it back and drops its temporary work tables. Use a fresh session. No raw business rows or Auth records are returned. Only four authority columns of `public.users` are read; private HR rows are not read. Function definitions are hashed rather than returned. The fixed reviewed seven-table new-business inventory reports presence and row counts, with unresolved counts for the promotion/schedule/visit request ledgers; it never returns their rows. Baseline construction and baseline reconciliation require all seven absent; committed reconciliation requires all seven present and empty with zero new-family unresolved requests. Missing proof or a committed proposal/tombstone is REVIEW_REQUIRED, with no cleanup or retry. Counts and old-column fingerprints cover existing PO/SJ/audit, Girard, promotions, assignments, schedules, visits/photos, old private request payload/result/tombstone data and Storage objects/buckets.

Obtain the exact final `schemaChanges` through a separately reviewed local rehearsal against a verified target-compatible schema. Each changed metadata key requires its exact `before` and `after` MD5 (or null for absence) and a nonempty reason. This is an explicit object-by-object list, not a prefix allowlist or acceptance of an arbitrary post-state. Review function identity/body/owner/ACL, table/column grants, RLS, policies, constraints, indexes, triggers and sequence definitions. Any unlisted change aborts. HR/auth/role/default-grant deltas, generic PO/SJ/audit table-policy ACL deltas, and every metadata/ACL change to an existing generic PO/SJ/audit column are refused even if listed. The only eligible generic additions are purchase_orders.sales_person_id_at_creation, sales_assignment_source_id, sales_attributed_at, sales_attribution_state and po_line_items.product_id. SQL independently checks their exact types, nullability and defaults, absence of column grants, and absence of identity/generated behavior; a matching supplied hash cannot authorize a different shape or grant.

Build with `buildDemoRollout({repoRoot,target,manifest,manifestSha256,baseline,schemaChanges})`. Sources normally load from the fixed migration paths; an explicit source array is useful for isolated tests and must match the same manifest. `baseline` is the approved preflight JSON object, including `columns`, `schema`, complete absent `new_tables` proof, data/schema fingerprints, pending inventory, database and operator. Hosted pending inventory must still be two and unresolved old requests zero. A changed business inventory requires renewed review, not editing a hash to proceed.

The result contains `sql`, `transactionSql`, `readbackSql`, fragment byte ranges and SHA-256s, and whole-packet/transaction/source-manifest hashes. `assertDemoRollout({...inputs,sql})` rebuilds and rejects any byte change. Strict parsing removes only each verified outer `BEGIN;`/`COMMIT;`; one outer transaction encloses all four exact bodies, guards and `NOTIFY`. Unexpected top-level transaction control, psql commands and malformed wrappers fail closed. There is no partial-apply fallback.

## Intended permissions that require exact enumeration

The final `schemaChanges` must enumerate the exact observed changes and hashes for these intended categories; this list alone is not a machine-readable approval:

- New private promotion ledgers and identity sequences deny PUBLIC/anon/authenticated access. New private helper functions deny those roles except authenticated execution of `private.demo_can_upload_promotion(text,text)`.
- `public.promotions` loses direct mutation/DDL-like table privileges for PUBLIC/anon/authenticated; `promotions_write` becomes false. Four new public promotion read/write/reconcile functions grant authenticated execution after revoking PUBLIC/anon access.
- Storage adds only `demo_promotion_upload`, `demo_promotion_insert_guard`, `demo_promotion_no_raw_read`, `demo_promotion_no_raw_update` and `demo_promotion_no_raw_delete` policies. Existing visit objects, buckets and policies are preserved.
- New private visit/schedule ledgers/audit/helper functions deny direct PUBLIC/anon/authenticated access. `public.visit_requests` allows authenticated SELECT under `visit_requests_current_scope`; existing schedules lose direct INSERT/UPDATE/DELETE, and visits/photos lose direct UPDATE/DELETE. New public schedule transaction/reconcile/store-context endpoints grant authenticated execution.
- Reporting grants authenticated execution, without PUBLIC/anon execution, for the new canonical/admin sales source, admin sales start and sales-report-month functions. Existing replaced read functions retain reviewed metadata/grants.
- Assignment cardinality changes no ACLs and no business rows. Generic PO/SJ/audit policies and table grants, untouched function metadata, role memberships, default privileges, HR and reset behavior remain unchanged.

If an observed delta falls outside these intentions, stop for review. Never bless every observed difference simply because it came from a rehearsal.

## Uncertain outcomes and rollback boundary

An interrupted/lost response is **not a failed transaction**. Do not reapply. Retain the original packet/hash, confirm whether the prior session still exists and perform readback through the same verified target. `BASELINE_INTACT` means the old baseline was observed, not authorization to rerun while the original transaction may still be active; confirm it ended, refresh preflight, review the busy/drain cause and obtain any changed-scope authorization first. `COMMITTED_STATE_VERIFIED` means exact expected metadata, old-column data, bounded additive-column metadata/default state, all seven empty new tables, zero new-family unresolved requests and private bucket were observed; correlate it with the retained manifest/transaction. It is a state proof, not a durable database migration ledger. `REVIEW_REQUIRED` includes drift, later business writes or an incomplete/unknown state and never requests automatic reapply.

Precommit failure rolls back all four migrations. After commit, especially after new business writes, recover compatible services or prepare a reviewed forward correction. Do not drop new ledgers/stock/evidence, rewrite recovery tombstones, restore the incompatible old client alone, or claim a data-preserving reverse migration exists. Destructive repairs or restore actions require explicit authority and validated recovery evidence.
