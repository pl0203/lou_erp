## Boundaries and semantics

- New plans, lines, monthly roster, active projection, immutable events, request ledger and history-coverage attestation are private, RLS enabled and denied to client roles. Public wrappers have a fixed empty search path, explicit active-role checks, and no default execution grants.
- Manager proposes only their own verified team. Their verified Head **or** executive independently approves, never the proposer. Salespeople can discover/read only their own published lines, with `baselineSnapshot: null` so predecessor planning evidence cannot leak.
- Current canonical portfolios drive planning, including predecessor customer history solely as customer/month aggregates. Customer-known legacy PO/SJ history may be included for planning only through an internal flag; dashboards exclude unknown legacy credit, and no legacy Girard/non-PO estimates are mixed in. Actual PO/CO credit is never rewritten. Existing legacy `public.sales_targets` is untouched.
- Baseline recommendations require three completed Asia/Jakarta calendar months. Six months are context. PO source-history completeness needs an explicit private attestation of the `po-known-customer-including-legacy-v1` source policy, absent by default; a first transaction is not proof of coverage. CO complete months require a current full-month report and effective generation. Unknown is not a zero baseline.
- Dashboard PO/SJ amounts are exact **recorded eligible ledger** aggregates; zero recorded rows is zero and does not attest complete historical capture for planning. CO dashboard reporting duty follows immutable batch-credit exposure in the effective generation: positive opening stock or any movement during the month requires full coverage. A settlement month still requires its report; subsequent settled gaps and PO-only customers have no invented duty and yield recorded zero. Required missing/partial reports retain missing/partial quality. Transferred carried stock stays in the original credited person’s cohort even without current-month allocations. Five KPI stages remain separate.
- Transfer warnings include predecessor-credit history, any-age predecessor `confirm`/`in_progress` PO (conservative open-order review), and positive predecessor CO stock in the effective generation. An explicit reason is required even when the proposed target equals a complete baseline.
- Monetary writes support up to 24 integer digits plus 2 decimals (`numeric(26,2)`), never JavaScript floating-point persistence. Zero target is distinct from missing/N/A. Mixed target/N/A totals and filtered-customer actuals have no comparable person-target denominator.
- Published monthly leaves stay under their publication manager. Current hierarchy fallback excludes an already published leaf elsewhere. Daily priorities and pending-review queues use the **current** hierarchy independently of frozen monthly financial reporting. Current-month activity excludes future schedules; visits count distinct salesperson/customer/business-day, while today matched schedules use exact schedule ID/person/customer linkage.
- Dashboard search/attention operates before totals and pagination. Sort is allowlisted, exact numeric, nulls last and stable. Trend contains two completed periods using the same selected authorized cohort, without reattribution.
- Every command has an actor/request ledger key, exact payload matching and optimistic version. Request advisory locks serialize retries/reconciliation. Reconcile waits for an in-flight same request and can read committed receipts while capability is disabled, after current authority checks; it cannot mutate/re-enable anything. Other data/command wrappers fail closed while disabled.
- Role/assignment table SHARE locks precede validation, then manager/month and plan locks. This intentionally conservative locking blocks authority/assignment drift atomically; it needs staging concurrency/load review. Unique active `(person,month,metric)` prevents overlap across managers. Published revisions/audit are immutable; supersession is atomic. Authorized manager/reviewer plan reads include the latest 100 narrow audit events with prior/new lines, reason, actor, timestamp and stored person names, plus an explicit truncation flag. Revision events retain the prior published values; salesperson projections and command receipts expose no audit events. Stale submissions may be returned with a reason for explicit roster refresh, but not approved.

## Local verification

Run `node scripts/test-sales-targets-ci.mjs` with local PostgreSQL 17 binaries available through `SALES_TARGETS_PG_BIN` (the local fallback is the sibling unpacked runtime). Node 24 supports direct TypeScript contract decoding; no new production dependency is required.

The runner never accepts a database URL or an existing cluster. It clears inherited PostgreSQL/database settings, creates a fresh owned temporary cluster, binds **only 127.0.0.1**, verifies PostgreSQL 17 and loopback, then stops/removes it. AF_UNIX socket startup was unsupported by this executor (`Operation not permitted`); loopback startup used ordinary tool execution without escalation. Any genuine tool/policy denial must stop testing rather than change access controls.

The default test-only source projections are hand-written and fictional. They install the exact fixed-baseline canonical-owner/credit helper bodies and triggers; negative tests change helper body/security/grants or disable source triggers and require fail-closed rejection. Suites cover reads, roles, portfolios, reporting, commands, edge cases, activity, full-filter sort/attention/trend, 0/5/42 customers and 0/3/30 added-rep scale. Concurrent sessions cover approval races, edit/submit, request replay, role revocation, assignment drift/stale return, overlapping plans and pending reconciliation. Cross-manager active uniqueness is also executed. Protected source counts/digests, immutable sales credit and legacy targets must match before/after. Actual SQL output is decoded by the frontend TypeScript decoders and emitted to `/tmp/sales-targets-contract-samples` for local review only.

Run `node scripts/test-sales-targets-ci.mjs --full-source` for the additional fixed-baseline source-composition check. It creates a separate loopback-only cluster on the existing CO fixture port, invokes the unchanged guarded CO runner through stage 08 (including its topology, role, lifecycle and race checks), then installs the additive target candidate and runs rollback-only own/team/baseline/command smoke checks. It does not impersonate CI or accept an external database.

## Remaining application gates

Synthetic results do not establish hosted source/ACL parity, real actor-role login behavior, production query plans, or workload capacity. The synthetic 42-customer planning case is bounded by a 15-second statement timeout, not a production performance certification. Facts and transfer flags are materialized once per customer; a larger batch aggregation may still be appropriate after measured staging plans.

Before any approved install, verify the exact target project, source migration/function definitions and privileges, coverage-attestation evidence, immutable-credit/source counts and digests, expected source indexes, application commit, and the exact least-privilege wrapper-grant manifest. `01` rejects missing source columns/unique ownership and exact canonical-owner/immutable-credit helper body, metadata, privilege and trigger drift before creating target objects. `04` repeats the read-only source guard plus capability-off/postflight ACL checks. Expected SHA-256 bodies are pinned to the stated repository baseline, never inferred from migration names. These checks are not a complete hosted attestation. Review all new wrapper permissions and source disclosure before an exact application-time approval. No automatic migration, notification, grant or enablement is performed by these files.

Rollback before a failed transaction is ordinary transaction rollback. After installation, disable the capability and restore the previous app; retain plans/audit. Revoke only the separately approved new wrapper grants if needed. Never drop history, modify operational sources, convert legacy targets, or weaken existing access.
